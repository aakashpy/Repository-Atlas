# Usage Guide

## One-time setup for a new project

Easiest path — an interactive script that asks for every setting (repo
path, embedding/reranker/LLM model choice, thresholds), validates what it
can right then (repo exists, Qdrant reachable, embedding model actually
loads and its real dimension is detected automatically, Ollama reachable
if chosen), and writes `config.yaml` for you:

```bash
python3 backend/setup_config.py
```

Backs up any existing `config.yaml` first. Offers to run the preflight
checker (below) immediately after.

Or edit `backend/config.yaml` by hand:

```yaml
project:
  name: "your_project_name"        # used to derive Qdrant collection names
  repo_path: "path/to/your/repo"
```

Adjust other settings if needed (relevance thresholds, LLM backend,
chunk sizes) — see `config.yaml`'s comments for what each controls. Either
way, if you changed the embedding model, reranker model, or LLM backend
(not just `project.name`/`repo_path`), run the preflight checker:

```bash
python3 backend/check_config.py
```

This confirms the configured models actually load and every external
service (Qdrant, the LLM backend) is reachable — in seconds, before you
commit to a multi-hour ingest that might fail partway through on a typo'd
model name or a missing API key.

Then run:

```bash
# 1. Index the current state of the codebase -- this alone is enough for a
#    fully working tool. Fast (minutes even for a large repo).
python3 backend/ingestion/ingest.py

# 2. Optional: backfill full commit history, so questions about *how the
#    code evolved* work too, not just how it works today. This can take
#    hours on a repo with a lot of history (it re-embeds every commit) --
#    safe to interrupt and resume (see "History is optional" below).
python3 backend/history/history_ingest.py

# 3. Install the git hook so future commits auto-update whichever of the
#    above you're using (see docs/SETUP.md, step 9)
```

### Recalibrating relevance thresholds after an embedding model change

`retrieval.min_score_current`/`min_score_history` are tuned to the specific
embedding model's score distribution — they do NOT automatically transfer
to a different model. After swapping `embedding.model_name` and re-running
`ingest.py`, run the checker's calibration stage:

```bash
python3 backend/check_config.py --calibrate
```

This scores a batch of deliberately off-topic questions and a batch of
on-topic questions (generated by your configured LLM from real chunks in
the freshly-ingested collection), then suggests a `min_score_current` value
sitting between the two — paste it into `config.yaml`. Treat it as a
starting point, not a guarantee: it's based on a small, automatically
generated sample, not a large hand-labeled set.

## History is optional

`history.enabled` in `config.yaml` (default `true`) controls whether the
system looks for history at all:

```yaml
history:
  enabled: true   # set to false to skip history entirely
```

You don't have to choose upfront, and you don't have to wait for a backfill
to finish before using the tool:

- **Current-state search always works on its own.** `search_history_raw()`
  degrades to an empty result — never an error — if history is disabled,
  hasn't been ingested yet, or a query against it fails for any reason
  (e.g. a re-ingest that's still in progress). `generate.py`/`chat.py`
  already treat "no history evidence" as a normal case, not a failure.
- **The check is live, not cached.** If you start `history_ingest.py` in
  the background while the web UI or CLI is already running, history
  questions start working the moment enough data exists — no restart
  needed.
- Set `history.enabled: false` if you don't want history at all (skips
  `history_ingest.py`/`history_update.py` outright, with a friendly message
  instead of doing any work) — useful for a quick look at a repo, or a repo
  whose history isn't interesting/available.

## Asking questions

```bash
python3 backend/generation/generate.py how does authentication work
python3 backend/generation/generate.py how has authentication changed over time
python3 backend/generation/generate.py why does my request hang forever
```

This is the main entry point for one-off CLI questions — it searches both
current code and history, and returns a synthesized, LLM-generated answer.
For a multi-turn conversation from the CLI, use `python3 backend/generation/chat.py`.

## Web UI

```bash
cd backend
uvicorn main:app --reload
```

Open `http://127.0.0.1:8000`. FastAPI (`backend/main.py`) serves both the
`/api/chat` endpoint and the static frontend (`frontend/`) from the same
process, so there's no separate frontend server or CORS setup needed. The
page is a single chat view plus a side panel that shows exactly which
current-code and history chunks were retrieved and sent to the LLM for
each turn — the same `search_raw`/`search_history_raw` results used
elsewhere, not a separate code path. Conversation history is kept
client-side in the browser and resent with each request; the backend
itself is stateless.

## Raw search (no LLM, just retrieval — useful for debugging)

```bash
# Current code only
python3 backend/retrieval/search.py PreparedRequest

# History only
python3 backend/retrieval/search_history.py dependency version bump
```

Useful when you want to see exactly what chunks were retrieved, without
the LLM's synthesis layer — e.g. to verify an answer is properly grounded.

## Switching LLM backend

In `config.yaml`'s `llm.backend` (`"gemini"` or `"ollama"`), or by editing
`BACKEND` in `backend/generation/generate.py`:

```python
BACKEND = "gemini"   # cloud, free tier, better reasoning (default)
BACKEND = "ollama"   # local, free, fully private, weaker reasoning
```

## Checking system state

```bash
# How many chunks are currently stored (current-state collection)
python3 backend/dev/count_points.py

# Find all stored chunks for a specific file (debugging)
python3 backend/dev/check_file.py <partial_filename>
```

## Evaluation tools (backend/dev/)

`backend/dev/` holds scripts built for testing and measuring this project
itself -- debugging utilities and evaluation tooling -- kept separate from
the subpackages that make up the actual running system (`backend/core/`,
`ingestion/`, `history/`, `retrieval/`, `generation/`). None of these are
imported by `main.py` or any other production code path.

```bash
# Real Recall@6 / MRR against a 22-question hand-labeled gold set
python3 backend/dev/eval_retrieval.py

# Automated faithfulness/relevancy judging of full generated answers
# (two LLM calls per question -- paced to respect free-tier rate limits)
python3 backend/dev/eval_rag.py

# Compares default vs. exact vs. different hnsw_ef values on the same
# eval set -- see docs/DECISIONS.md, "HNSW/ANN: Measured, Not Tuned"
python3 backend/dev/eval_hnsw.py

# Sweeps reranking.candidate_pool sizes and measures cross-encoder token
# truncation -- see docs/DECISIONS.md, "Reranker's Own Assumptions Validated"
python3 backend/dev/eval_reranker.py
```

## Manually triggering an update (without committing)

Normally the git hook does this automatically. To run manually:

```bash
python3 backend/ingestion/update_index.py      # current-state update
python3 backend/history/history_update.py      # adds latest commit to history
```

## Full rebuild (if something seems broken)

```bash
python3 backend/ingestion/ingest.py           # wipes and rebuilds current-state collection
python3 backend/history/history_ingest.py     # wipes and rebuilds FULL history (slow — see note below)
```

**Warning:** `history_ingest.py` reprocesses the entire git history from
scratch (took a meaningful amount of time on a 6,500-commit repo). Only
run this if the history collection is genuinely corrupted — not for
routine maintenance.

## Note on config changes

If you change `project.name` in `config.yaml`, you're pointing at a
*different* set of Qdrant collections — any previously ingested data
under the old name stays untouched (not deleted), but won't be
searched until you switch `project.name` back. Running `ingest.py` /
`history_ingest.py` again after a name change starts fresh collections
under the new name, not migrate the old ones.
